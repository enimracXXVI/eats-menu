eats Tab — reference

Database schema

The Google Sheet is the database — every tab below is a real sheet, every column here is a real header row. backend/Code.gs is the only thing that reads or writes it; this page documents what it expects to find. If a column here doesn't match the sheet, or the sheet has a column not listed here, that's a bug against this page.

A few things that aren't obvious from the sheet alone

ID columns display with a letter prefix (U00001, M00002, P00003…) — that's a Sheets number format on the column, not the stored value. Every ID underneath is a plain integer. Code that generates or compares IDs must never expect a string prefix.

Timestamps are always Europe/Rome, hardcoded in Code.gs regardless of the spreadsheet's own timezone setting (which Code.gs forces to match on every request) — never the ambient Apps Script project timezone.

Booleans are real Sheets checkboxes (TRUE/FALSE), not the strings "true"/"false".

Nothing is ever hard-deleted except a rejected/approved pending edit's own row. A removed menu item just gets active set to FALSE; it stays in the sheet.

users

Everyone who can log in. Login is username-only — no password — so this tab is the entire authorization list.

ColumnTypeNotes
user_idnumberPrimary key. Assigned as max existing + 1.
usernamestringLowercased on write. What's typed on the login screen — matched case-insensitively.
display_namestringShown everywhere in the app instead of the username.
is_superuserbooleanSuperusers' own menu edits apply immediately and skip the approval queue; only a superuser can review others' pending edits or delete a user.
activebooleanA deactivated user sees "This account is deactivated" instead of "User not authorised" on login — the two are deliberately different messages.

menu

The catalog. A row is never deleted — removing an item just sets active to FALSE, so historical purchases rows referencing it stay meaningful.

ColumnTypeNotes
item_idnumberPrimary key. Referenced by pendingEdits.item_id and purchases.item_id.
namestringEditable by anyone via a pending edit (immediate if a superuser proposes it).
pricenumber2-decimal amount, in whatever currency settings.currency is currently set to — there's no per-item currency.
activebooleanFALSE once removed. getMenu filters these out by default; Admin's bundle asks for them too, so a still-pending edit against an already-removed item can still show its last known name/price.

favorites

Each user's own starred items on the Menu tab — a plain join table between users and menu. No id column: the (user_id, item_id) pair is already unique and is exactly what every read/write here looks up by, so a synthetic id would carry no information a real lookup doesn't already have (same reasoning as the id-less settings tab). One row per favorited item per user; un-favoriting deletes the row rather than flagging it inactive.

ColumnTypeNotes
user_idnumberReferences users.user_id.
item_idnumberReferences menu.item_id.

pendingEdits

Every proposed menu change, approved or not — this is both the live approval queue (status = pending) and its own history.

ColumnTypeNotes
edit_idnumberPrimary key.
typestring (enum) new_item · rename · price_change · edit · remove_item
For an edit against an existing item, this is classified server-side at proposal time (classifyItemEdit in Code.gs), by comparing the proposed name/price against the item's current row — rename if only the name changed, price_change if only the price did, edit if both did. The client never chooses this value directly; it only ever sends a generic intent, so the stored type is always an accurate description of what the edit actually does, not a guess made in the UI.
item_idnumberBlank for new_item — there's no existing item to reference yet.
proposed_namestringThe item's name after this edit applies (unchanged from its current name, if only the price changed).
proposed_pricenumberThe item's price after this edit applies (unchanged from its current price, if only the name changed, or if this is a removal — a snapshot of the price at the moment of proposal).
user_idnumberProposer's users.user_id.
proposed_bystringProposer's username, denormalized for display without a join.
proposed_attimestampYYYY-MM-DDTHH:MM, Europe/Rome.
statusstring (enum) pending · approved · rejected
Set to approved immediately (never pending) when a superuser proposes their own edit.
reviewed_bystringBlank until reviewed. The superuser's username who approved/rejected it (or, for a self-approved superuser edit, the proposer themself).
reviewed_attimestampBlank until reviewed. YYYY-MM-DDTHH:MM, Europe/Rome.

purchases

One row per distinct item per checkout (a 3-item cart writes 3 rows in one batched call). Everything here is a snapshot at the moment of purchase — it doesn't move if the item is later renamed or repriced.

ColumnTypeNotes
purchase_idnumberPrimary key.
user_idnumberWho logged it. A purchase can only be deleted by this same user, and only on the same day (see date).
usernamestringSnapshot, denormalized for display.
item_idnumberReferences menu.item_id — but see item_name/unit_price below, since the menu row itself may have changed since.
item_namestringSnapshot of the item's name at purchase time.
unitsnumberQuantity bought in this line.
unit_pricenumberSnapshot of the item's price at purchase time.
price_paidnumberunits × unit_price, stored rather than recomputed.
datedateYYYY-MM-DD, Europe/Rome. Drives "today's" filtering everywhere and the same-day delete rule.
timestamptimestampYYYY-MM-DDTHH:MM, Europe/Rome.

settings

The one tab that isn't row-per-record — it's a plain key/value pair per row (column A = key, column B = value), read as a single object.

KeyTypeNotes
daily_allowancenumber2-decimal amount. What the Today ticket and header chip measure spending against.
currencystring (enum) EUR · GBP · USD · CAD · AUD · BRL · COP
Always picked from this fixed list (Admin's Settings card is a <select>, never free text) — every price display in the app depends on it being one of these seven.
