Canteen Tally — reference

Style guide

Every component the app uses, in its real markup and real CSS — nothing on this page is redrawn or approximated. Hover or tap anything below and you're seeing its actual :hover / :active state. If a button looks different somewhere in the app, that's a bug against this page, not a second style.

The app itself (.app-shell) is a centered, phone-width card up to 900px viewport width, floating with a shadow from 540px up. Past 900px — a real desktop window, not just a wider phone — it fills the window edge-to-edge instead, with its header/screen/ nav/cart-bar content capped at a comfortable 720px reading width and centered within it. This page isn't the app shell, so none of that applies here — see db-schema.html for the sheet itself.

Buttons

Exactly one modifier per button. Never mix — a screen must never show two different styles for the same kind of action (e.g. two different "confirm" looks).

.btn .btn--primary — the single commit action on a screen (Log purchase, Save settings, Continue)

Default → hover lightens to --color-paprika-strong → active scales to 97%. Disabled drops to 40% opacity.

.btn .btn--outline — secondary / neutral action (+ Propose a new item)
.btn .btn--safe / .btn .btn--critical — Admin approvals only

Outline by default; hover fills solid. This fill-on-hover is reserved for approve/reject — no other button fills on hover.

.btn--icon — small circular icon-only button (Menu screen: propose-edit pencil · Header: log out). .btn--icon--critical — the destructive variant (delete item), an inline SVG line-icon colored via currentColor, never an emoji.
.btn--block full width · .btn--sm compact, used inside the cart bar
Busy state — every button that fires a request (Save, Send for review, Approve/Reject, Log purchase, the switches, every delete) disables itself and swaps its label for the duration, so a slow round trip can't be fired twice by an impatient second tap. Shown here mid-request.

Approve/Reject specifically are paired: clicking one disables and hides the other, so the busy one expands to fill the row (via the existing flex:1 on both) instead of leaving a still-tappable sibling next to a button that says "Approving…" — see .approval-row below.

Menu's catalog rows (above): leading .star-btn favourites the item (see Badges above). .row--tappable darkens on hover/active. Tapping the row itself toggles it in/out of the cart — a second tap removes it, it does not keep incrementing. .row--selected + .qty-badge together mark an item already in the cart; tapping the badge (not the row) is what adjusts quantity. .badge--pending replaces the edit button while a change is queued — a superuser never sees this state on their own edits, which apply immediately, but does see it (as a tappable badge, opening a review sheet) on anyone else's.

Every favorited item also appears in a "Favourites" section at the top of the Menu tab (same row markup, reused as-is) — it collapses away entirely rather than showing an empty state once nothing is favorited.

.approval-row — Admin › Waiting on your approval. The category (New item / Rename / Price change / Edit / Remove) is folded into the "X proposes" line in paprika, not a separate badge — and it's the sheet's own type column, classified once server-side when the edit was proposed (comparing the proposed name/price against the item's current row), not re-guessed on this screen. Name and price sit on one row via .edit-summary, each showing a struck-through previous value next to the proposed one whenever that field actually changed.

The handle is a real drag surface, not a button — a tap does nothing; only dragging it down past ~35% of the sheet's height (or a fast flick, however short) dismisses it, tracking the finger 1:1 with no lag. Anything short of that eases back open. Tapping the backdrop or the phone/browser back button also closes the sheet, via a pushed history entry that's popped on close.

.sheet__title-row — an optional header action next to the title, e.g. the delete-item trash icon on an existing item's edit sheet. Also used, with the title itself set to the edit's category, for the Menu tab's inline review sheet (Approve/Reject on a pending edit without detouring through Admin).

Edit Croissant

Item names are editable here, not locked — a typo is fixed the same way a price is. Superuser: applies immediately. Anyone else: queued, same as a price change.

confirmDialog() — the on-brand replacement for the browser's native confirm(), used for every destructive confirmation (delete a user, delete a menu item). Same sheet, same drag/backdrop/back dismissal — resolves false if dismissed any way other than tapping Delete.
